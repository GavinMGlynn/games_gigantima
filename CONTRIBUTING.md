# Contributing

Patches, maps, dialogue, bug reports and replay files are all welcome. This file
is what you need to know before sending one; `CLAUDE.md` is the longer statement
of how the project is built and why, and it is worth reading if you plan to
change code.

## The quickest useful contribution is content

**Content is data, not C.** Adding a person, a creature, a quest, a spell or a
map is an edit to a file in `assets/` — no code, no rebuild of anything but the
game you already have:

| | |
| --- | --- |
| `assets/dialogue.txt` | who lives in the world and everything they say |
| `assets/bestiary.txt` | what lives in the hills, and where it is found |
| `assets/quests.txt` | the story, as stages and the conditions that enter them |
| `assets/spells.txt` | the runes, and the phrases they make |
| `assets/maps/*.ggmap` | the maps, written by `gigantima_editor` |

Each file documents its format at the top. The game names the file and the line
it did not understand and refuses to load a broken one, so a mistake is a
message rather than a mystery. See [PLAYING.md](PLAYING.md#making-a-map-of-your-own).

If you send content, say what you tested it with — "walked it start to finish on
seed 12" is plenty.

## Building

```sh
git clone https://github.com/GavinMGlynn/games_gigantima.git
cd games_gigantima
git submodule update --init --depth 1 ext/sdl ext/sdl_image

cmake --preset linux-release          # or windows-release, macos-release
cmake --build --preset linux-release
ctest --preset linux-release
```

C23 is required: **GCC 14+, Clang 19+, AppleClang 16+, or MSVC 19.39+**. You do
**not** need `ext/lpc-revised` — that is 766 MB of source art, needed only to
regenerate the atlases, and the generated output is committed.

## What a change has to do

- **`ctest` stays green.** A red tree is the stop-everything condition.
- **Warnings are errors**, in every build type, `-Wconversion` and
  `-Wsign-conversion` included. They are the two that actually catch defects in
  a codebase this full of tile arithmetic.
- **Build with more than one compiler before you send it.** GCC and Clang do not
  warn about the same things; CI has both, plus MSVC, and finding out there is
  slower for everybody.
- **`src/core/` may not know how anything is drawn, heard or typed at.** It may
  use SDL for memory, files, logging and string formatting, but never a
  renderer, window, event, gamepad or audio stream. This is checked at configure
  time by `cmake/Layering.cmake`, not remembered.
- **The simulation is integer-only and seeded.** No floating point and no
  wall-clock time in `src/core/`, ever — `--seed N` reproducing a world exactly
  is a feature, and `--replay` depends on it.
- **The world advances only inside `gg_game_act`.** Animation runs at 60 Hz
  whether or not the world moved. Do not blur that line.

## Tests

**One item at a time, landing with its test.** Name a test as a sentence stating
the fact it pins — `the_camera_moves_in_sub_tile_steps_while_walking` — so a
failure reads as a claim that stopped being true.

A test that only sometimes tests its rule is worse than no test, because the
green tick is not evidence. If a test depends on what the generator happened to
produce, build the situation explicitly instead.

**Check your test by breaking the thing it pins** and watching it fail. Nearly
every bug listed at the bottom of `docs/COMPLETION_PLAN.md` was found that way,
or would have been.

## Documentation moves with the code

Two documents are living, and a change that makes either of them wrong is not
finished:

- `docs/PROJECT_STATUS.md` — what now works, and how it was verified. This is
  the single source of truth; if it and the code disagree, the file is the bug.
- `docs/COMPLETION_PLAN.md` — a **user** document. One or two sentences per item
  and a verification in plain English. Implementation detail goes in the status,
  never here.

Anything you learn the hard way goes at the bottom of the plan under *Tails
found while building*, the moment you learn it.

## Reporting a bug

[PLAYING.md](PLAYING.md#reporting-a-bug) has the detail. In short: a replay file
is the best possible bug report, and a seed and a turn count is the next best.

```sh
./gigantima --profile Bug --new --play --record bug.ggreplay
./gigantima --replay bug.ggreplay
```
